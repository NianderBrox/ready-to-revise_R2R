# Ready to Revise Database Design

## 1. Purpose

This document defines the logical data model for the Ready to Revise backend.

Its purpose is to describe the business entities, their relationships, constraints, and design principles before implementation. This document serves as the source of truth for the database architecture. The Prisma schema is considered the implementation of this design.

---

# 2. Database Standards

## Primary Keys

- Every entity uses a UUID as its primary identifier.
- The primary key is always named `id`.

## Audit Fields

Every major entity contains:

- createdAt
- updatedAt

## Soft Delete

Major entities support soft deletion through a deletedAt field.

Records are never permanently removed unless explicitly required.

## Naming

- Entity names use PascalCase.
- Field names use camelCase.
- Relationship names are descriptive.
- Every entity has a single responsibility.

## Images

Images are never stored inside the database.

Only metadata and references to image storage locations are stored.

---

# 3. Design Principles

The database follows these principles:

- Store facts, not calculations.
- Separate business entities by responsibility.
- Prefer normalization over duplication.
- Keep AI-generated data separate from user-generated data.
- Store files outside the database.
- Design for future expansion.
- Every entity must have a clear owner and lifecycle.

---

# 4. Non-Goals

The database does not:

- Store image binary data.
- Store temporary OCR jobs.
- Store AI prompts.
- Store derived analytics.
- Store cached values that can be recalculated.

# 5. Core Entities

## User

### Purpose

Represents a registered user of the application.

### Owner

System

### Lifecycle

Registered

↓

Authenticated

↓

Uses application

↓

May be deactivated

↓

Soft deleted

---

## Subject

### Purpose

Represents a top-level academic subject.

Examples include Mathematics, Physics, Chemistry, and Biology.

### Owner

System

---

## Topic

### Purpose

Represents a chapter or concept within a subject.

Examples include Integration, Electrostatics, Organic Chemistry, and Probability.

### Owner

Subject

---

## Question

### Purpose

### Owner

### Lifecycle

↓

Image Uploaded

↓

OCR Processed

↓

AI Analysis Generated

↓

Revision Scheduled

↓

Reviewed Multiple Times

↓

Archived

↓

Soft Deleted

# 6. Supporting Entities

## OCRResult

Stores the extracted text from the uploaded image along with cleaned text and OCR confidence information.

---

## AIAnalysis

Stores metadata generated by AI including:

- difficulty
- concepts
- keywords
- formulas
- estimated solving time
- tags

AIAnalysis never modifies the Question itself.

---

## RevisionSchedule

Stores only the current spaced repetition state.

Responsibilities include:

- next revision
- current interval
- ease factor
- memory score

Only one active revision schedule exists per question.

---

## RevisionAttempt

Represents one completed revision session.

Each attempt stores historical information and is never updated after creation.

This entity exists for analytics and learning history.

---

## Notification

Represents reminders and system notifications delivered to a user.

---

# 7. Relationships

Business relationships are defined as follows:

- One User owns many Questions.
- One User receives many Notifications.
- One Subject contains many Topics.
- One Topic contains many Questions.
- One Question has one OCRResult.
- One Question has one AIAnalysis.
- One Question has one RevisionSchedule.
- One Question has many RevisionAttempts.

---

# 8. Constraints

The following business rules must always hold:

- Every Question belongs to exactly one User.
- Every Question belongs to exactly one Topic.
- Every Topic belongs to exactly one Subject.
- Every Question has exactly one active RevisionSchedule.
- AI analysis must never overwrite original question information.
- Images are referenced, not stored.

---

# 9. Indexing Strategy

The following data should be optimized for lookup:

- User email
- Question ownership
- Topic lookup
- Subject lookup
- Upcoming revisions
- Notification delivery

Additional indexes may be introduced as usage patterns become clear.

---

# 10. Future Expansion

The current design allows future support for:

- Flashcards
- Shared question libraries
- Collaborative study groups
- AI tutor conversations
- Multi-language OCR
- Offline synchronization
- Multiple OCR providers
- Multiple AI providers
- Learning analytics
- Exam-specific categorization
